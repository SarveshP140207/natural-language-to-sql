\# Natural Language to SQL — Project Context



\## 1. Project Overview



This project is a production-oriented Natural Language to SQL system.



The system allows a user to ask questions in normal human language, converts the question into SQL using an AI model, validates the generated SQL, executes it safely against a MySQL database, and presents the result in an understandable format.



Example:



User:

"Which 10 products generated the highest revenue?"



System:

Natural language → intent analysis → schema retrieval → SQL generation → SQL validation → MySQL execution → result analysis → response/visualization



The project must be a functional working system, not a static demo or mockup.



\---



\## 2. Primary Goal



Build a reliable AI-powered system that can:



1\. Understand natural-language database questions.

2\. Automatically understand the database schema.

3\. Retrieve only the relevant schema information.

4\. Generate SQL using an LLM.

5\. Validate generated SQL before execution.

6\. Execute safe queries against MySQL.

7\. Explain the results in natural language.

8\. Generate useful visualizations when appropriate.

9\. Support conversational follow-up questions.

10\. Maintain query history.

11\. Handle SQL errors and attempt controlled query repair.

12\. Provide schema information to the user.

13\. Use RAG for schema metadata, relationships, business rules, and SQL examples.

\## 5. Security Rules



These rules are mandatory.



1\. Never directly execute SQL generated by the LLM.

2\. Every generated query must be parsed and validated.

3\. The initial system must be read-only.

4\. Only SELECT and safe WITH/CTE queries are allowed initially.

5\. Block INSERT.

6\. Block UPDATE.

7\. Block DELETE.

8\. Block DROP.

9\. Block ALTER.

10\. Block TRUNCATE.

11\. Block CREATE.

12\. Block GRANT.

13\. Block REVOKE.

14\. Never use the MySQL root account for query execution.

15\. Use a dedicated read-only database user.

16\. Apply query execution limits.

17\. Apply result row limits.

18\. Apply appropriate timeout controls.

19\. Never expose database passwords or API keys to the frontend.

20\. Never commit `.env` files or secrets to GitHub.

\## 7. Database Introspection



The application must NOT rely on hardcoded database schema information.



It must automatically inspect MySQL and discover:



\- databases

\- tables

\- columns

\- column types

\- primary keys

\- foreign keys

\- indexes

\- constraints

\- relationships



The introspected information should be converted into canonical schema documents.



A schema hash/version should be maintained so that changes to the database can trigger re-indexing.



\---

RAG should primarily contain:



\- table descriptions

\- relationships

\- primary/foreign keys

\- SQL examples

\- useful database documentation



The system should retrieve only the schema information relevant to the current question.

\## 9. SQL Generation



The LLM should return structured information rather than unrestricted text.



Expected logical output:



\- intent

\- SQL

\- tables\_used

\- explanation

\- assumptions

\- visualization suggestion



The SQL must pass validation before execution.



The SQL generator must use retrieved schema context rather than assuming database structure.



\---



\## 10. Ambiguous Questions



If a question cannot be safely interpreted, the system should ask the user for clarification rather than guessing.



Example:



User:

"Show me the best products."



Possible clarification:



"Do you mean best by sales revenue, quantity sold, customer ratings, or another metric?"



Avoid silently making important assumptions.



\---



\## 11. Conversational Queries



The system should eventually support questions such as:



User:

"Show the top 5 customers by spending."



Then:



"Now show their order count."



Then:



"Only include customers from last year."



The system should maintain appropriate conversation context while still validating every generated query independently.



\---



\## 12. Query Repair



If a validated SQL query fails during execution:



1\. Capture the database error.

2\. Analyze the error.

3\. Provide the error and relevant schema context to the repair process.

4\. Generate a corrected SQL query.

5\. Validate the corrected query again.

6\. Execute only if validation succeeds.

7\. Retry a maximum of 2 times.



Never bypass validation during repair.



\---



\## 13. Result Intelligence



After successful execution, the system should:



\- display the result in a clean format

\- summarize important findings

\- identify useful trends where appropriate

\- recommend a visualization when useful

\- generate charts using Plotly when appropriate



Do not create charts for every query.
